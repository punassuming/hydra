## 1. Onboarding & Auth Flow

*Investigating: Domain token vs admin token distinction, error handling, token expiry*

### Findings

**File:** `ui/src/components/AuthPrompt.tsx` (lines 1-145)

**Strengths:**
- Single unified form is simpler than separate sign-in modes (contradicts AGENTS.md claim of "clearly separated")
- Graceful degradation: if admin token fails validation, proceeds with domain-only access + warning message (line 52)
- Domain input defaults to "prod" (sensible default for common case)
- Clear field labels distinguish domain token from admin token
- "Optional" label on admin token helps users understand they can skip it
- Helper text under domain token clarifies shared use with workers (line 97)

**Issues:**
- Error messages are generic: "Invalid domain token" or "Invalid admin token" (lines 197, 205 in client.ts) — doesn't help users understand WHY (wrong format? expired? revoked? wrong domain?)
- Form resets completely when switching domains (AuthPrompt.tsx line 22-26) — feels jarring, loses admin token input if already entered
- No indication of token expiry or when admin token was last validated
- No "forgot token?" or recovery workflow
- 401 errors from subsequent API calls trigger re-showing auth modal (line 127 in client.ts) but no context about what changed (token revoked? expired? domain changed?)
- No inline validation feedback — errors only appear after clicking Connect

**UX Recommendation:**
Add error context (e.g., "Invalid token — verify token format and that the domain exists") and preserve admin token input across domain switches (until explicitly cleared). Consider showing when tokens were last validated in the header/settings after login.

## 2. Navigation & Information Architecture

*Investigating: Header nav clarity, page hierarchy, task flow coherence, duplicated views*

### Findings

**Files:** `ui/src/App.tsx` (lines 65-81), `ui/src/pages/Home.tsx`, `ui/src/pages/Observe.tsx`, `ui/src/pages/History.tsx`, `ui/src/pages/JobDetail.tsx`

**Strengths:**
- Header nav is clean: three main tabs (Operate/Observe/Workers) + Admin button + Settings (App.tsx line 65-71)
- "Operate" (Home) provides single-page dashboard for most common tasks: create job, see upcoming/queued jobs, see selected job's history, see live events
- JobDetail page provides multiple specialized views (Grid, Gantt, dependency Graph) for analyzing job runs
- Job creation → editing → manual run all available on Home page without navigation (modal-based, modal-based for create/edit)

**Issues — Information Architecture Problems:**
- **History duplication** (UX anti-pattern): Job history appears in 3+ places:
  1. Home page's "Job History" card (selected job only, line 327-329)
  2. Observe page (with Status & History tabs)
  3. Dedicated History page at `/history`
  4. JobDetail page (multiple tabs: Runs, Grid, Gantt)
  - User doesn't know where to go to see "all job runs for a domain" vs "all runs of one job" vs "runs with filters"
  - No clear signposting: History page is not visible in main nav, only reachable via URL or if explicitly looking

- **Task flow friction**: To "create job → watch run → debug failure → retry":
  1. Create job on Home (modal)
  2. To monitor: stay on Home's "Job History" card (only shows selected job) OR navigate to Observe OR go to JobDetail
  3. To view logs: click "View Logs" in History table → opens RunInspector side panel
  4. To retry: must navigate back and click "Run Selected" OR use backfill on JobDetail
  - Switching between Home and Observe breaks flow (tab click = page reload, state reset)

- **Observe page confusion**: Shows two tabs (Status / History) but unclear purpose vs Home vs separate History page
  - Status tab shows "JobOverview" with mini run-status strips (line 32-50 in Observe.tsx)
  - History tab duplicates the History page

- **Missing breadcrumb/context**: Admin page is a button in header, not in nav hierarchy; users may not know settings/domain management is there

**UX Recommendations:**
1. **Consolidate history views**: Decide: is History global (per-domain) or per-job? Expose the answer clearly.
   - Global view on Home or Observe with domain-wide search/filters
   - Per-job view embedded in JobDetail (already done well)
   - If both needed, cross-link them explicitly
2. **Clarify Observe page purpose**: Either merge into Home (reduce tab count) or make Observe a dedicated analytics/KPI page distinct from operational control
3. **Add breadcrumb** or modal title that shows where you are (e.g., "Home > Jobs > Edit Job XYZ" when editing)
4. **Persist job selection across page reloads**: Currently selecting a job on Home and switching to Observe loses selection

## 3. Job Creation Flow

*Investigating: Form complexity, AI shortcut integration, defaults, validation feedback*

### Findings

**Files:** `ui/src/components/job-form/index.tsx` (1330 lines), `ui/src/components/job-form/defaults.ts`, component submodules (PlacementSection, CompletionSection, etc.)

**Strengths:**
- Magic Job Generator is available on new job creation (Alert box, lines 1160-1181) with provider selector (Gemini/OpenAI)
- Excellent defaults: executor type defaults with auto-adjusted timeout (EXECUTOR_DEFAULTS in defaults.ts), sensible field values (line 27-70)
- Smart form behavior: editing a job with non-default advanced values auto-expands Advanced Settings (lines 164-188, 224)
- Validation feedback: "Validate" button shows cron preview and next-run-at (lines 1068-1075)
- Import/Export JSON for job definitions (lines 1186-1187)
- Non-Persistent run option: test a job without saving (line 1296)
- Executor-type-aware UI: shows only relevant fields per executor (shell, python, sql, http, sensor, batch, powershell — lines 463-829)

**Issues — Form Complexity & Cognitive Overload:**
- **Massive form**: 8 executor types each with different field sets; Schedule section with cron presets, timezone, start/end dates; Advanced Settings with 7 sub-sections (Placement, Completion, Notifications, Auth, Source, Retry Advanced, Misc)
- **Magic Job Generator is under-featured**: Shows as an info Alert at the top (line 1161) — not visually prominent as a primary entry point. Users scanning the form see "Name" field before they see "Generate with AI"
- **No progressive disclosure on initial view**: Form shows all basic fields at once (Job Definition, Schedule) before toggling Advanced. New users see 20+ fields before learning Advanced exists
- **Step 1/Step 2 implied but no visual step markers**: Lines 1190 and 1247 comment "Step 1" and "Step 2" but no step counter/progress indicator in the UI
- **Validation only on click**: No inline/real-time feedback (e.g., "name is required" as you type) — users only discover errors after clicking Validate/Submit
- **No field help text for most fields**: Few tooltips except "Retries" (line 1229). Users creating their first HTTP or Sensor job face unknown fields with no guidance
- **Too many action buttons at bottom** (line 1280-1319): Submit, Validate, Run Non-Persistent, Run Now, New Job, Cancel — unclear which is the "happy path"

**UX Recommendations:**
1. **Elevate Magic Job Generator**: Redesign as a modal/primary option card (e.g., "Start with AI ✨ | Start from template | Start blank") before showing the form
2. **Reduce initial cognitive load**: Hide Advanced Settings by default (✓ already done), but also consider hiding less-common executor types behind "More" dropdown initially (show Shell, Python, HTTP; hide Batch, PowerShell, Sensor under "More")
3. **Add field help**: Hover tooltips or collapse/expand help for each executor type explaining what it does
4. **Inline validation**: Show name-required error as you leave the field, not just on submit
5. **Step counter**: Add "Step 1 of 2: Job Definition | Step 2: Advanced Settings" markers to guide new users
6. **Clarify action buttons**: Rename "Run Non-Persistent" to "Save & Test" and highlight the Submit button as the primary action (currently all same size)

## 4. Monitoring & Debugging Flow

*Investigating: Path from failure detection to AI analysis, retry/backfill options*

### Findings

**Files:** `ui/src/components/JobRuns.tsx`, `ui/src/components/RunInspector.tsx`, `ui/src/components/FailureInsight.tsx`, `ui/src/pages/JobDetail.tsx`

**Strengths:**
- Single RunInspector drawer (lines 26-127 in RunInspector.tsx) consolidates run details across all pages (unified design, no drifting implementations)
- Live log streaming for running jobs (lines 53-67 in RunInspector.tsx) with stdout/stderr tabs (LogViewer component)
- FailureInsight component (lines 21-176 in FailureInsight.tsx) offers multiple analysis modes:
  - "Failure fix" (root cause analysis via LLM)
  - "Summary" (run summary)
  - "Error extraction" (pull errors from logs)
  - "Retry tuning" (timing advice)
  - "Custom question" (ask about logs)
- "Compare vs Last Success" (Run Diff Copilot, lines 59-75): Diffs failed run against last successful run + p90 duration baseline, shows confidence level (high/medium/low) and is_transient flag
- Manual run and backfill buttons visible on JobDetail page (lines 320-321)
- Quick access: "View Logs" link in JobRuns table opens RunInspector (line 77 in JobRuns.tsx)

**Issues — Multi-Click Debugging Workflow:**
- **No direct retry from failed run**: To retry a failed run, user must:
  1. See failed run in JobRuns table
  2. Click "View Logs" to open RunInspector drawer
  3. Close drawer
  4. Click "Run Now" button on JobDetail header (line 320) to run the entire job again
  - Missing: "Retry this run with same params" button in RunInspector
  
- **Backfill discoverability**: Backfill button on JobDetail (line 321) but not visible from:
  - Home page's "Job History" card (no buttons exposed)
  - Observe page's History tab
  - RunInspector drawer (when viewing a failed run)
  - User sees a failure, wants to re-run it on past dates, but must navigate away and find the Backfill button

- **AI analysis requires scrolling**: FailureInsight (showing AI analysis options) appears at the bottom of RunInspector drawer below LogViewer (line 96 in RunInspector.tsx). Users must:
  1. View logs (often scroll through them)
  2. Scroll down to see AI analysis options
  3. Click one and wait for LLM
  - For a failed job, this is the critical insight, but it's below-the-fold

- **No context about root cause before clicking Analyze**: FailureInsight shows options (Failure fix, Summary, etc.) but no preview of what each does. Users must click and wait.

- **No quick recommendation from RunInspector**: If a run is still running (not failed yet), user can't easily see the job definition or parameters that triggered this run from within the drawer.

**UX Recommendations:**
1. **Add "Retry" button in RunInspector**: Quick re-run of same job with same params (or let user adjust params before running)
2. **Surface Backfill from RunInspector**: "This failed on date X. Backfill runs from [date] to [date]?" action, especially for failed sensor/recurring jobs
3. **Move FailureInsight above logs**: Show AI options at top of RunInspector (after run metadata) with a compact "Analyze failure" button that shows a dropdown (Failure fix | Summary | Custom question) vs full UI at bottom
4. **Collapse/expand logs by default**: Show first 1KB of logs by default, "Expand" to see full tail, so FailureInsight is visible without scrolling
5. **Cross-link job params in RunInspector**: Show which job definition and params triggered this run (especially useful for manual runs with custom env vars)

## 5. Worker Management Flow

*Investigating: Capacity/health visibility, onboarding ease*

### Findings

**Files:** `ui/src/pages/Workers.tsx`, `ui/src/pages/WorkerDetail.tsx`, `ui/src/components/WorkerSetupDrawer.tsx`

**Strengths:**
- Dashboard cards at top (Workers.tsx lines 287-305): "Workers Online", "Running Tasks", "Avg Memory", "Avg Load" — quick at-a-glance capacity health
- Comprehensive table with columns: Worker ID, Affinity & Capabilities, Runtime, Saturation, Dispatch status (lines 59-183)
- Saturation column (lines 114-135) shows running/max concurrency with progress bar and visual overflow alert ("over quota via bypass jobs")
- State control buttons (Online/Drain/Offline/Detach) right in the table (lines 146-175) — no modal required
- WorkerSetupDrawer (WorkerSetupDrawer.tsx) provides multi-deployment-mode guidance:
  - Docker Compose
  - Bare-metal / VM
  - Windows
  - Kubernetes
  - Step-by-step instructions with copy-able code blocks
- Worker Detail page includes:
  - Metrics trend charts (memory, CPU load, etc. via custom SVG mini-charts)
  - Concurrency timeline/Gantt view showing job execution per worker
  - Worker operations log with event history
- Execution window (24h) showing all jobs on a timeline across all workers

**Issues — Onboarding Clarity & First-Time Experience:**
- **WorkerSetupDrawer is text-heavy**: Step-by-step instructions assume user knows their deployment target (Docker vs Kubernetes vs bare-metal). No guidance like "Choose Docker if you have Docker installed locally" or "Choose Kubernetes if you're deploying to a cluster"
  
- **Placeholder tokens in setup instructions**: Code blocks show `<your-domain-token>`, `<redis-acl-password>` — these are placeholders but users must know WHERE to get these tokens
  - Domain token location: not mentioned (where do they get it? Admin panel? CLI?)
  - Redis password: only available after Redis ACL is rotated via admin API
  - No cross-link to "Generate credentials" flow

- **No "quick start" path**: New user sees "Connect Worker" button → opens setup drawer → 4 deployment mode options → lots of text. No "I just want to test with Docker" shortcut

- **Worker status is one-way**: Can see worker is "offline" but no quick link to "Why is this offline?" or "Re-run diagnostics"

- **No worker lifecycle guidance**: Missing docs on:
  - When to use Drain vs Offline
  - How long to wait for graceful drain
  - What happens to running jobs during failover

**UX Recommendations:**
1. **Simplify WorkerSetupDrawer**: Add a "Recommended for me" path (detect browser/OS? show Docker first if available) before full multi-mode choice
2. **Cross-link credentials**: "Need a token? Generate domain credentials" button in setup drawer that opens Admin or pops out to credential generation flow
3. **Add worker troubleshooting**: Offline worker card shows "Last heartbeat: 5 minutes ago" with a "Diagnose" action that checks Redis connectivity, API auth, etc.
4. **Step counter in setup**: "Step 1 of 4: Choose Deployment Mode" to guide users
5. **Clarify state transitions**: Tooltip on Online/Drain/Offline buttons explaining each state (Drain = stop accepting new jobs, wait for current to finish)

## 6. Admin & Domain Self-Service

*Investigating: Credential/template/domain management intuitiveness*

### Findings

**Files:** `ui/src/pages/Admin.tsx` (700+ lines)

**Strengths:**
- Clear card-based layout: "Domain Token Rotation", "Current Domain Settings", "Create Domain" (admin-only), "Domains" table (admin-only), "Credentials", "Import Jobs" (demo mode)
- Token rotation is self-service: domain users can rotate their own token + Redis ACL without admin help (lines 405-433)
- Credentials are write-only (line 478) — prevents accidental secret exposure in logs/screenshots
- Credential types are flexible: Database (with dialect picker), API Key, Generic (lines 97-161)
- Domain/credential scoping is clear: buttons/forms show which domain they apply to (e.g., line 475: "Credentials (domain: ${isAdmin ? credDomain : activeDomain})")
- Demo mode (controlled by `HYDRA_DEMO_MODE` env var) has special "Import Jobs" section with built-in templates and sample loader (lines 609-676)

**Issues — Credential Setup Friction & First-Time Workflow:**
- **Credentials require explicit creation**: New domain has no credentials. To use SQL/HTTP jobs:
  1. Go to Admin page
  2. Create a credential with all fields (dialect, username, password, host, port, database)
  3. Remember the credential name to use in job definitions
  - Missing: Inline help like "This credential will be used in jobs via `executor.credential_ref = 'prod-db'`"

- **Token rotation has two UX flows**: 
  - Line 426-427: Rotate My Domain Token (quick button)
  - Line 429-431: Rotate My Redis ACL (separate button)
  - But a modal (line 396-403) says "modal will show a ready-to-run command with actual credential values"
  - Unclear: does rotating domain token also show a modal? When do workers get new credentials?

- **Admin-only vs domain user actions not visually distinct**: 
  - Create Domain card (line 436) appears for admins
  - Domains table (line 465) appears for admins
  - But other cards (Current Domain Settings, Credentials) appear for both
  - No visual separation or "ADMIN ONLY" badge on admin-exclusive sections

- **Credentials table shows no preview**: Can see Name, Type, Dialect, Updated At — but no "Test Connection" button to verify credentials work before using them in jobs

- **Domain creation requires exact naming**: Line 446 shows domain input but no validation UI. AGENTS.md says "2-63 chars, lowercase letters/numbers with optional `_`/`-`, must start/end with alphanumeric" — not shown in form

- **No quick "add credential" from job form**: When creating a SQL job (needs a credential_ref), user must:
  1. Save job as draft (or create it)
  2. Navigate to Admin page
  3. Create credential
  4. Go back and edit job to use it
  - Missing: "Need a new credential?" link in JobForm SQL section

**UX Recommendations:**
1. **Inline credential help**: Add a "How to use this credential in jobs" section on the Credentials card explaining `executor.credential_ref` usage
2. **Add "Test" button**: For database credentials, offer a quick "Test Connection" action to verify before saving
3. **Distinguish admin sections visually**: Add a "ADMIN ONLY" badge or use a different card style for Create Domain, Domains table
4. **Clarify token rotation workflow**: After clicking "Rotate My Domain Token", show modal with: (a) new token, (b) where to use it (worker setup, new domain login), (c) when old token expires
5. **Domain name validation UI**: Show validation rule inline ("2-63 chars, lowercase, alphanumeric + dash/underscore") as user types
6. **Quick credential creation from JobForm**: When setting `credential_ref` in SQL executor, offer "Create new credential" link that opens a modal/drawer without leaving the job form

## 7. Empty & Error States

*Investigating: Actionability of empty states, error message helpfulness*

### Findings

**Files:** `ui/src/components/JobRuns.tsx`, `ui/src/pages/JobDetail.tsx`, `ui/src/pages/WorkerDetail.tsx`, `ui/src/pages/Home.tsx`

**Strengths:**
- Loading states: Tables show loading spinners (ant Design Table component handles this)
- Component-level error messages: JobDetail line 277 "Job not found" and WorkerDetail "Worker not found" when resource missing
- Table empty states: Using ant Design's `locale={{ emptyText: "..." }}` for consistent messaging (e.g., WorkerDetail "No running jobs on this worker")
- Status messages on Home page (line 242): transient message feedback at top of card when actions succeed/fail

**Issues — Poor Discoverability & Actionability of Empty States:**
- **"Select a job" message is passive**: JobRuns.tsx line 93 shows "Select a job to view run history." but:
  - Doesn't explain WHERE to select a job (Home page? JobDetail? Observe?)
  - No link to go select a job
  - User must infer to go back to Home and click a job
  
- **No onboarding for empty domains**: First time user lands on Home with zero jobs:
  - Sees "Upcoming Jobs" table (empty), "Queued Jobs" table (empty), "Jobs" list (empty), "Job History" card (empty)
  - No banner/alert saying "No jobs yet — Create one!" with a link
  - Must find the "New Job" button in the action bar (line 222-223)

- **No "first run" guidance**: Empty "Job History" card doesn't say "Run a job to see history here"

- **Error messages lack context**: FailureInsight.tsx line 68-70: Error message can be:
  - "no_prior_success" → "No successful run of this job exists yet to compare against."
  - Generic catch: "Failed to compare against last success: ${message}"
  - But if the error is "network timeout" vs "job has no runs", user sees both as generic errors

- **No error recovery suggestions**: When a credential create/update fails (Admin page), just shows error message. Doesn't suggest "Check that your password is correct" or "Verify the host/port"

- **Tables with no data don't suggest action**: 
  - Worker list empty → no message
  - Credentials list empty → just "no data" (not shown explicitly but no helpful guidance)
  - History list empty → no "Create a job and run it" link

**UX Recommendations:**
1. **Add first-run banner on Home**: "No jobs yet? Create your first job →" when job list is empty (conditional rendering before JobList)
2. **Make JobRuns "Select a job" message actionable**: Add a link like "← Back to job list" or show a small list of recent jobs to select
3. **Contextual error messages**: Parse error messages from API and show user-friendly guidance (e.g., "Database connection failed" instead of raw error)
4. **Add "Create your first credential" banner on Admin page**: When Credentials table is empty, show "Add a credential to use in SQL/HTTP jobs →"
5. **Suggest action in empty tables**: Add an Alert component above empty tables (e.g., "No workers online — View worker setup guide")
6. **Loading skeletons instead of spinners**: For JobList/WorkerList, show skeleton placeholders while loading (feels faster than spinners)

## 8. Cognitive Load & Information Density

*Investigating: Page complexity, progressive disclosure patterns*

### Findings

**Files:** `ui/src/components/JobList.tsx` (300+ lines), `ui/src/pages/Workers.tsx` (400+ lines), `ui/src/pages/Home.tsx`, `ui/src/pages/JobDetail.tsx`

**Issues — Information Overload:**

1. **JobList table has 9+ columns** (JobList.tsx lines 81-205):
   - Name, Domain, User, Executor, Priority, Schedule (mode + time), Enabled (toggle), Retries, Updated, Actions (clone/delete)
   - Each row is tall due to tags (line 89-96) and multi-line Schedule renderer (line 112-126)
   - Horizontal scrolling required on small screens
   - Users scanning for a job must process: is it enabled? what's the schedule? when's it next? who owns it? — all at once
   - **Better pattern**: Collapse executor/priority/retries into a "Show more" expandable row detail, show only Name/Schedule/Status/Actions initially

2. **Workers table has 6 columns** (Workers.tsx lines 59-183):
   - Worker ID, Affinity & Capabilities (5 sub-rows of tags/text), Runtime (7 sub-rows), Saturation (progress bar), Dispatch (status + 5 buttons)
   - Each row is huge (visually takes 1/3 screen height)
   - User wants "quick health check" but sees: tags, shells, capabilities, Python version, CPU, memory, load, processes, users, saturation, state buttons
   - Multiple action buttons (Online/Drain/Offline/Detach) crammed into Dispatch column
   - **Better pattern**: Show only critical info (Worker ID, status, saturation, online/offline button) by default; expand for details

3. **Home page has 7+ cards/sections**:
   - JobsDashboard (large cards with KPIs)
   - QueueHealth (visual pressure gauge)
   - Upcoming Jobs table (6 rows visible)
   - Queued Jobs table (6 rows visible)
   - Jobs list (JobList with 9 columns)
   - Job History (JobRuns table for selected job)
   - Events feed
   - **Cognitive load**: "What's the status?" requires scanning 5-7 different sections. No single "health" view.

4. **JobForm has ALL fields visible at once** (until user toggles Advanced):
   - Name, Tags, Executor Type (8 options!), Timeout, Retries, then executor-specific fields (5-15 per type)
   - Schedule section with mode (immediate/cron/interval/dependency) then mode-specific fields
   - 30+ form fields before scrolling
   - New users are overwhelmed; experienced users waste time scrolling past defaults
   - **Better pattern**: Multi-step wizard or tab-based form (Basics | Schedule | Advanced)

5. **WorkerDetail page shows 3 complex views simultaneously**:
   - Metrics line chart (memory, CPU, load)
   - Concurrency lane timeline (Gantt-like view)
   - Operations event timeline
   - Each is data-rich; user must correlate events across 3 views manually
   - **Better pattern**: Synchronized timeline view where zooming one timeline zooms others; collapse metrics to sparklines initially

6. **Admin page is a mixed-bag**: 4-6 cards (Domain Settings, Create Domain, Domains table, Credentials, Import Jobs) with different purposes (self-service + admin admin + demo). No clear hierarchy.

**Progressive Disclosure Patterns Present (Good)**:
- JobForm: Advanced Settings toggle (line 1250-1276 in job-form/index.tsx) — auto-expands when editing jobs with non-defaults
- JobList: View mode toggle (Table vs Card, line 44 in JobList.tsx)
- Workers: No progressive disclosure — all details visible

**What's Missing**:
- Column visibility toggles on tables (show/hide less critical columns)
- Collapsible row details on JobList/Workers (expand to see full info)
- Dashboard view for first-time users (reduce to top 3 cards, hide advanced)
- Tabs or wizard for complex forms (JobForm, credential creation)
- Synchronized/correlated timelines (WorkerDetail)

**UX Recommendations:**
1. **Job List**: Show only Name, Schedule, Status, Enabled, Actions by default; offer column visibility toggle (hide Domain/User/Priority/Retries if unneeded); add expand-row detail
2. **Workers**: Show only ID, Status, Saturation, Single "Manage" button (which opens a modal with state buttons); expand for full details
3. **Home**: Replace 7 cards with 1-2 "Status" cards + expandable sections (Upcoming, Queued, History) - "fold" the view by default
4. **JobForm**: Convert to 3-step wizard (Basics → Schedule → Advanced) or tabbed layout
5. **WorkerDetail**: Single synchronized timeline view with metrics as mini sparklines; user can click to expand specific section
6. **Admin**: Split into "Self-Service" (Domain Settings, Credentials) and "Admin Only" sections with visual separation

## Summary — Top 5 Priorities

**Ranked by (user pain reduction) × (effort to implement):**

### 1. **Consolidate history views & fix task flow fragmentation** (Area 2)
- **Pain**: Creating job → watching run → debugging failure requires 3+ page switches, losing context; History appears in 3+ places (Home, Observe, dedicated History page)
- **Fix**: 
  1. Persist job selection across Operate/Observe tabs so switching tabs doesn't reset
  2. Expose one clear "per-domain history" view (recommend: Observe → History tab)
  3. Remove duplicate History page or cross-link clearly
- **Effort**: Low-medium (state management + routing tweak)
- **Impact**: Reduces friction in most common workflow (create → monitor → debug)

### 2. **Reduce Job Form complexity via progressive disclosure** (Area 3)
- **Pain**: 30+ form fields visible at once; new users overwhelmed; experienced users scroll endlessly past defaults
- **Fix**: Convert to 3-step wizard:
  1. Basics: Name, Executor Type, (executor-specific fields only)
  2. Schedule: Mode, Cron/Interval, Start/End times
  3. Advanced: Placement, Completion, Notifications, etc. (current Advanced Settings)
- **Effort**: Medium (refactor form component, add step navigation)
- **Impact**: Onboarding smoother; reduces errors from misconfig

### 3. **Add "Retry from RunInspector" + surface Backfill** (Area 4)
- **Pain**: Failed run → View logs → Close drawer → Click "Run Now" to retry (4 clicks). Backfill hidden on JobDetail, unreachable from failed run view.
- **Fix**:
  1. Add "Retry" button in RunInspector drawer
  2. Add "Backfill from this date" action in RunInspector (if run failed, pre-fill start date = failure date)
  3. Move FailureInsight above logs (or collapse logs by default)
- **Effort**: Low (UI additions + API call plumbing already exists)
- **Impact**: Critical path for ops: "I see a failure, I need to fix and re-run it"

### 4. **Redesign Home page as a unified status dashboard** (Area 2 + 8)
- **Pain**: 7 cards require scanning multiple sections to answer "what's the current state?"; Upcoming/Queued/History tables all visible at once (cognitive overload)
- **Fix**:
  1. Collapse Upcoming/Queued tables into one "Queue Status" card (expandable)
  2. Replace top-level "Job History" with per-job detail (keep only on JobDetail page)
  3. Fold Events feed into status (or move to Observe tab)
  4. Keep "New Job" + "From Template" buttons + JobsDashboard KPIs
  5. Result: 3-4 cards on initial load, expandable sections for details
- **Effort**: Medium (restructure layout, move JobRuns off Home)
- **Impact**: First-time users land on less overwhelming page; power users still have quick access to details

### 5. **Worker & Credential onboarding — reduce setup friction** (Area 5 + 6)
- **Pain**: 
  1. WorkerSetupDrawer shows 4 deployment modes + dense instructions; no "recommended for me" path
  2. Credentials require manual creation before first SQL/HTTP job; no inline "Create credential" from JobForm
  3. Workers page shows all details at once; new users can't distinguish critical info (online/offline) from metadata
- **Fix**:
  1. Detect browser/OS in WorkerSetupDrawer, pre-select "Docker" for Linux, "Windows" for Windows
  2. Add step counter "Step 1 of 4" in drawer
