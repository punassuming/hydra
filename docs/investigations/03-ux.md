## 1. Onboarding & Auth Flow

*Investigating: Domain token vs admin token distinction, error handling, token expiry*

### Findings

**File:** `ui/src/components/AuthPrompt.tsx` (lines 1-145)

**Strengths:**
- Single unified form is simpler than separate sign-in modes (contradicts AGENTS.md claim of "clearly separated")
- Graceful degradation: if admin token fails validation, proceeds with domain-only access + warning message (line 52)
- Domain input defaults to "prod" (sensible default for common case)
- Clear field labels distinguish domain token from admin token
- "Optional" label on admin token helps users understand they can skip it
- Helper text under domain token clarifies shared use with workers (line 97)

**Issues:**
- Error messages are generic: "Invalid domain token" or "Invalid admin token" (lines 197, 205 in client.ts) — doesn't help users understand WHY (wrong format? expired? revoked? wrong domain?)
- Form resets completely when switching domains (AuthPrompt.tsx line 22-26) — feels jarring, loses admin token input if already entered
- No indication of token expiry or when admin token was last validated
- No "forgot token?" or recovery workflow
- 401 errors from subsequent API calls trigger re-showing auth modal (line 127 in client.ts) but no context about what changed (token revoked? expired? domain changed?)
- No inline validation feedback — errors only appear after clicking Connect

**UX Recommendation:**
Add error context (e.g., "Invalid token — verify token format and that the domain exists") and preserve admin token input across domain switches (until explicitly cleared). Consider showing when tokens were last validated in the header/settings after login.

## 2. Navigation & Information Architecture

*Investigating: Header nav clarity, page hierarchy, task flow coherence, duplicated views*

### Findings

**Files:** `ui/src/App.tsx` (lines 65-81), `ui/src/pages/Home.tsx`, `ui/src/pages/Observe.tsx`, `ui/src/pages/History.tsx`, `ui/src/pages/JobDetail.tsx`

**Strengths:**
- Header nav is clean: three main tabs (Operate/Observe/Workers) + Admin button + Settings (App.tsx line 65-71)
- "Operate" (Home) provides single-page dashboard for most common tasks: create job, see upcoming/queued jobs, see selected job's history, see live events
- JobDetail page provides multiple specialized views (Grid, Gantt, dependency Graph) for analyzing job runs
- Job creation → editing → manual run all available on Home page without navigation (modal-based, modal-based for create/edit)

**Issues — Information Architecture Problems:**
- **History duplication** (UX anti-pattern): Job history appears in 3+ places:
  1. Home page's "Job History" card (selected job only, line 327-329)
  2. Observe page (with Status & History tabs)
  3. Dedicated History page at `/history`
  4. JobDetail page (multiple tabs: Runs, Grid, Gantt)
  - User doesn't know where to go to see "all job runs for a domain" vs "all runs of one job" vs "runs with filters"
  - No clear signposting: History page is not visible in main nav, only reachable via URL or if explicitly looking

- **Task flow friction**: To "create job → watch run → debug failure → retry":
  1. Create job on Home (modal)
  2. To monitor: stay on Home's "Job History" card (only shows selected job) OR navigate to Observe OR go to JobDetail
  3. To view logs: click "View Logs" in History table → opens RunInspector side panel
  4. To retry: must navigate back and click "Run Selected" OR use backfill on JobDetail
  - Switching between Home and Observe breaks flow (tab click = page reload, state reset)

- **Observe page confusion**: Shows two tabs (Status / History) but unclear purpose vs Home vs separate History page
  - Status tab shows "JobOverview" with mini run-status strips (line 32-50 in Observe.tsx)
  - History tab duplicates the History page

- **Missing breadcrumb/context**: Admin page is a button in header, not in nav hierarchy; users may not know settings/domain management is there

**UX Recommendations:**
1. **Consolidate history views**: Decide: is History global (per-domain) or per-job? Expose the answer clearly.
   - Global view on Home or Observe with domain-wide search/filters
   - Per-job view embedded in JobDetail (already done well)
   - If both needed, cross-link them explicitly
2. **Clarify Observe page purpose**: Either merge into Home (reduce tab count) or make Observe a dedicated analytics/KPI page distinct from operational control
3. **Add breadcrumb** or modal title that shows where you are (e.g., "Home > Jobs > Edit Job XYZ" when editing)
4. **Persist job selection across page reloads**: Currently selecting a job on Home and switching to Observe loses selection

## 3. Job Creation Flow

*Investigating: Form complexity, AI shortcut integration, defaults, validation feedback*

### Findings

**Files:** `ui/src/components/job-form/index.tsx` (1330 lines), `ui/src/components/job-form/defaults.ts`, component submodules (PlacementSection, CompletionSection, etc.)

**Strengths:**
- Magic Job Generator is available on new job creation (Alert box, lines 1160-1181) with provider selector (Gemini/OpenAI)
- Excellent defaults: executor type defaults with auto-adjusted timeout (EXECUTOR_DEFAULTS in defaults.ts), sensible field values (line 27-70)
- Smart form behavior: editing a job with non-default advanced values auto-expands Advanced Settings (lines 164-188, 224)
- Validation feedback: "Validate" button shows cron preview and next-run-at (lines 1068-1075)
- Import/Export JSON for job definitions (lines 1186-1187)
- Non-Persistent run option: test a job without saving (line 1296)
- Executor-type-aware UI: shows only relevant fields per executor (shell, python, sql, http, sensor, batch, powershell — lines 463-829)

**Issues — Form Complexity & Cognitive Overload:**
- **Massive form**: 8 executor types each with different field sets; Schedule section with cron presets, timezone, start/end dates; Advanced Settings with 7 sub-sections (Placement, Completion, Notifications, Auth, Source, Retry Advanced, Misc)
- **Magic Job Generator is under-featured**: Shows as an info Alert at the top (line 1161) — not visually prominent as a primary entry point. Users scanning the form see "Name" field before they see "Generate with AI"
- **No progressive disclosure on initial view**: Form shows all basic fields at once (Job Definition, Schedule) before toggling Advanced. New users see 20+ fields before learning Advanced exists
- **Step 1/Step 2 implied but no visual step markers**: Lines 1190 and 1247 comment "Step 1" and "Step 2" but no step counter/progress indicator in the UI
- **Validation only on click**: No inline/real-time feedback (e.g., "name is required" as you type) — users only discover errors after clicking Validate/Submit
- **No field help text for most fields**: Few tooltips except "Retries" (line 1229). Users creating their first HTTP or Sensor job face unknown fields with no guidance
- **Too many action buttons at bottom** (line 1280-1319): Submit, Validate, Run Non-Persistent, Run Now, New Job, Cancel — unclear which is the "happy path"

**UX Recommendations:**
1. **Elevate Magic Job Generator**: Redesign as a modal/primary option card (e.g., "Start with AI ✨ | Start from template | Start blank") before showing the form
2. **Reduce initial cognitive load**: Hide Advanced Settings by default (✓ already done), but also consider hiding less-common executor types behind "More" dropdown initially (show Shell, Python, HTTP; hide Batch, PowerShell, Sensor under "More")
3. **Add field help**: Hover tooltips or collapse/expand help for each executor type explaining what it does
4. **Inline validation**: Show name-required error as you leave the field, not just on submit
5. **Step counter**: Add "Step 1 of 2: Job Definition | Step 2: Advanced Settings" markers to guide new users
6. **Clarify action buttons**: Rename "Run Non-Persistent" to "Save & Test" and highlight the Submit button as the primary action (currently all same size)

## 4. Monitoring & Debugging Flow

*Investigating: Path from failure detection to AI analysis, retry/backfill options*

### Findings

**Files:** `ui/src/components/JobRuns.tsx`, `ui/src/components/RunInspector.tsx`, `ui/src/components/FailureInsight.tsx`, `ui/src/pages/JobDetail.tsx`

**Strengths:**
- Single RunInspector drawer (lines 26-127 in RunInspector.tsx) consolidates run details across all pages (unified design, no drifting implementations)
- Live log streaming for running jobs (lines 53-67 in RunInspector.tsx) with stdout/stderr tabs (LogViewer component)
- FailureInsight component (lines 21-176 in FailureInsight.tsx) offers multiple analysis modes:
  - "Failure fix" (root cause analysis via LLM)
  - "Summary" (run summary)
  - "Error extraction" (pull errors from logs)
  - "Retry tuning" (timing advice)
  - "Custom question" (ask about logs)
- "Compare vs Last Success" (Run Diff Copilot, lines 59-75): Diffs failed run against last successful run + p90 duration baseline, shows confidence level (high/medium/low) and is_transient flag
- Manual run and backfill buttons visible on JobDetail page (lines 320-321)
- Quick access: "View Logs" link in JobRuns table opens RunInspector (line 77 in JobRuns.tsx)

**Issues — Multi-Click Debugging Workflow:**
- **No direct retry from failed run**: To retry a failed run, user must:
  1. See failed run in JobRuns table
  2. Click "View Logs" to open RunInspector drawer
  3. Close drawer
  4. Click "Run Now" button on JobDetail header (line 320) to run the entire job again
  - Missing: "Retry this run with same params" button in RunInspector
  
- **Backfill discoverability**: Backfill button on JobDetail (line 321) but not visible from:
  - Home page's "Job History" card (no buttons exposed)
  - Observe page's History tab
  - RunInspector drawer (when viewing a failed run)
  - User sees a failure, wants to re-run it on past dates, but must navigate away and find the Backfill button

- **AI analysis requires scrolling**: FailureInsight (showing AI analysis options) appears at the bottom of RunInspector drawer below LogViewer (line 96 in RunInspector.tsx). Users must:
  1. View logs (often scroll through them)
  2. Scroll down to see AI analysis options
  3. Click one and wait for LLM
  - For a failed job, this is the critical insight, but it's below-the-fold

- **No context about root cause before clicking Analyze**: FailureInsight shows options (Failure fix, Summary, etc.) but no preview of what each does. Users must click and wait.

- **No quick recommendation from RunInspector**: If a run is still running (not failed yet), user can't easily see the job definition or parameters that triggered this run from within the drawer.

**UX Recommendations:**
1. **Add "Retry" button in RunInspector**: Quick re-run of same job with same params (or let user adjust params before running)
2. **Surface Backfill from RunInspector**: "This failed on date X. Backfill runs from [date] to [date]?" action, especially for failed sensor/recurring jobs
3. **Move FailureInsight above logs**: Show AI options at top of RunInspector (after run metadata) with a compact "Analyze failure" button that shows a dropdown (Failure fix | Summary | Custom question) vs full UI at bottom
4. **Collapse/expand logs by default**: Show first 1KB of logs by default, "Expand" to see full tail, so FailureInsight is visible without scrolling
5. **Cross-link job params in RunInspector**: Show which job definition and params triggered this run (especially useful for manual runs with custom env vars)

## 5. Worker Management Flow

*Investigating: Capacity/health visibility, onboarding ease*

### Findings

**Files:** `ui/src/pages/Workers.tsx`, `ui/src/pages/WorkerDetail.tsx`, `ui/src/components/WorkerSetupDrawer.tsx`

**Strengths:**
- Dashboard cards at top (Workers.tsx lines 287-305): "Workers Online", "Running Tasks", "Avg Memory", "Avg Load" — quick at-a-glance capacity health
- Comprehensive table with columns: Worker ID, Affinity & Capabilities, Runtime, Saturation, Dispatch status (lines 59-183)
- Saturation column (lines 114-135) shows running/max concurrency with progress bar and visual overflow alert ("over quota via bypass jobs")
- State control buttons (Online/Drain/Offline/Detach) right in the table (lines 146-175) — no modal required
- WorkerSetupDrawer (WorkerSetupDrawer.tsx) provides multi-deployment-mode guidance:
  - Docker Compose
  - Bare-metal / VM
  - Windows
  - Kubernetes
  - Step-by-step instructions with copy-able code blocks
- Worker Detail page includes:
  - Metrics trend charts (memory, CPU load, etc. via custom SVG mini-charts)
  - Concurrency timeline/Gantt view showing job execution per worker
  - Worker operations log with event history
- Execution window (24h) showing all jobs on a timeline across all workers

**Issues — Onboarding Clarity & First-Time Experience:**
- **WorkerSetupDrawer is text-heavy**: Step-by-step instructions assume user knows their deployment target (Docker vs Kubernetes vs bare-metal). No guidance like "Choose Docker if you have Docker installed locally" or "Choose Kubernetes if you're deploying to a cluster"
  
- **Placeholder tokens in setup instructions**: Code blocks show `<your-domain-token>`, `<redis-acl-password>` — these are placeholders but users must know WHERE to get these tokens
  - Domain token location: not mentioned (where do they get it? Admin panel? CLI?)
  - Redis password: only available after Redis ACL is rotated via admin API
  - No cross-link to "Generate credentials" flow

- **No "quick start" path**: New user sees "Connect Worker" button → opens setup drawer → 4 deployment mode options → lots of text. No "I just want to test with Docker" shortcut

- **Worker status is one-way**: Can see worker is "offline" but no quick link to "Why is this offline?" or "Re-run diagnostics"

- **No worker lifecycle guidance**: Missing docs on:
  - When to use Drain vs Offline
  - How long to wait for graceful drain
  - What happens to running jobs during failover

**UX Recommendations:**
1. **Simplify WorkerSetupDrawer**: Add a "Recommended for me" path (detect browser/OS? show Docker first if available) before full multi-mode choice
2. **Cross-link credentials**: "Need a token? Generate domain credentials" button in setup drawer that opens Admin or pops out to credential generation flow
3. **Add worker troubleshooting**: Offline worker card shows "Last heartbeat: 5 minutes ago" with a "Diagnose" action that checks Redis connectivity, API auth, etc.
4. **Step counter in setup**: "Step 1 of 4: Choose Deployment Mode" to guide users
5. **Clarify state transitions**: Tooltip on Online/Drain/Offline buttons explaining each state (Drain = stop accepting new jobs, wait for current to finish)
